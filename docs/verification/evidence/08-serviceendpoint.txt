FINDING and its resolution: the identifier changes on update

  A did:oyd is the hash over {doc, key}. If the serviceEndpoint changes, the
  hash changes -- in this method there is no update without a new identifier.
  The identifier that was issued stays resolvable, because resolution follows
  the log chain through to the current document.

  On the question whether canonicalId may additionally appear in equivalentId:
  DID Core does not expressly govern the relation between the two sets, but it
  defines canonicalId as "identical to the equivalentId property except: (a) it
  is associated with a single value rather than a set, and (b) the DID is
  defined to be the canonical ID for the DID subject". A canonicalId therefore
  IS, by definition, an equivalentId with an additional property; including it
  in the set is consistent and not forbidden -- and it is the safer variant,
  because a consumer reading only equivalentId would otherwise get an
  incomplete list.

  The point is therefore NO LONGER a deviation. Two remarks remain for the
  method specification: equivalentId obliges the METHOD to guarantee logical
  equivalence -- that argument belongs written out, not left implicit in the
  resolver. And DID Core has a STABLE canonical form in mind for canonicalId;
  here it moves with every update, which the wording permits ("in the scope of
  the containing DID document") but which should be explained.
