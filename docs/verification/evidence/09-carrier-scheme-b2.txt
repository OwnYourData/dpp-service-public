Scheme B2: a self-certifying carrier identifier — 2026-08-23

Subject
  Product DID    did:oyd:zAkk4XNgY3rjJLXvWgRraEM4Nmfm      (blake2b-18)
  Data carrier   https://dpp.oydapp.eu/zAkk4XNgY3rjJLXvWgRraEM4Nmfm
                 = 8 + 13 + 1 + 28 = 50 characters, the registry's upper limit
  Passport DID   did:oyd:zQmSPHjWjTvADKxd9V1wiFAwDpR2WcA864zsrS3fQichvwS
  Custodian      dpp.data-vault.eu, collection 4

  The carrier's path is the multibase multihash of the product DID, without the
  prefix did:oyd:. Dropping it is lossless as long as the DID carries no
  location suffix; checked, none present.

  The content of the product DID does NOT contain the carrier URL. It cannot:
  the path is the hash over exactly this document, so an address contained in it
  would be part of its own computation. The same circularity from which it
  follows that the serviceEndpoint goes through the ProductID.

1 — Self-certification
  oydid read did:oyd:zAkk4XNgY3rjJLXvWgRraEM4Nmfm --show-verification

  confirms step by step:
      the identifier is the hash of the DID document
      the log reference in the document is the hash of the TERMINATE log entry
      no revocation entry can be found

  The printed string therefore commits to a document rather than merely
  addressing one -- without a ledger and without an external trust anchor.

2 — The same string, two readings
  as a web address  https://dpp.oydapp.eu/zAkk4XNgY3rjJLXvWgRraEM4Nmfm
                    -> HTTP 200, the product passport

  as a DID          did:oyd:zAkk4XNgY3rjJLXvWgRraEM4Nmfm
                    -> id = did:oyd:zAkk4XNgY3rjJLXvWgRraEM4Nmfm
                       payload = {name: Lumina LED 806lm, model: L-806-E27,
                                  manufacturer: Lumina}

  Whoever wants to treat the identifier as a DID prepends eight characters;
  whoever treats it as an address calls it. The consumer path needs no
  additional software (prEN 18219, 4.6.2 (2)), and the DID semantics are
  available all the same.

3 — The same checks as for scheme A

4 — What B2 costs, against scheme A
  Granularity had to be DECLARED. Under scheme A the service derives it from the
  path (/21/ = item) and refuses a declaration the path contradicts; here the
  path says nothing and the service has to believe the declaration. prEN 18223,
  Table 1 requires the value but does not require it to be true -- under A it is
  checked, under B2 it is not.

  What also falls away is what section 3 of the scheme-A evidence shows: getting
  GTIN and serial number out of the scan alone. The identifier identifies; it
  does not describe.

5 — And the limit the method cannot pass
  blake2b-18 is 144 bits, so 2^72 work for a collision. The threat model is
  narrow but not academic: only someone who produces BOTH documents can exploit
  it -- for a DPP that is the manufacturer, and it is precisely against his
  later reinterpretation that a self-certifying identifier is meant to protect.
  A third party would need 2^144.

  2^72 blake2b evaluations are within reach of state or large-industrial actors
  and get cheaper over a product's lifetime. The long-term guidance from BSI and
  NIST is 128 bits.

  128 bits are NOT reachable under the registry's 50-character limit: that would
  need a 32-byte digest, so more than 45 characters of path. The registry's
  limit forces the compromise, not the architecture.

  The only lever is the hostname; one label fewer is worth a factor of 4096:
      dpp.oydapp.eu   13 characters   path 28   blake2b-18   2^72
      oydapp.eu        9 characters   path 32   blake2b-21   2^84
      pace.eu          7 characters   path 34   blake2b-22   2^88
      dpp.eu           6 characters   path 35   blake2b-23   2^92

  Mitigation without a longer printed string: additionally record the full
  sha2-256 hash of the DID document in the registry entry. The short identifier
  is then the pointer, the 128-bit commitment exists regardless, and a later
  substitution shows up on comparison.

Tooling
  oydid CLI 0.8.3 on gem 0.8.2. The lengths are deterministic, not "at most":
  the leading code byte is small and constant, so the digit count does not tip.
  blake2b-18 gives exactly 28 characters, blake2b-19 exactly 29.
